Title: Best practices — Getting started with Codex and proven practices for better results
These are task-focused notes from the supplied text, not a change to Codex configuration.

Practices to apply
1. Start each coherent task with the goal, relevant files/context, constraints, and observable completion evidence.
2. Plan complex work before editing. Keep the plan current as findings change. Describe the user behavior and preservation requirements before implementation details.
3. Keep durable repository guidance short in AGENTS.md. Put a repeated, bounded verification workflow in SKILL.md; add rules in response to repeated mistakes rather than hypothetical edge cases.
4. Give subagents bounded tasks and explicit file ownership. Avoid concurrent writers on the same files; use an isolated worktree when concurrent work truly needs overlapping files.
5. Review each change and neighboring flows, then run the relevant checks. A successful build does not prove rendered behavior, account isolation, provider responses, or device behavior.
6. Check the actual working directory, installed versions, available tools and permissions. Verify unstable product/API details in official documentation rather than assuming the pasted examples remain current.
7. Add MCP connections only when they remove a specific manual loop. Add supporting scripts when they improve reliability. Stabilize a manual workflow before scheduling it.
8. Keep one chat focused on one coherent outcome. Preserve accepted decisions and evidence across compaction; fork when the work actually branches.

Application to the current approved work
- Goal: implement all 16 individually approved app-review proposals.
- Product constraints: Weeks only; copied setup and daily notes stay independent; completion resets for a new Week; previous records remain unchanged; personalization, spirituality and Gemini stay optional.
- Scope: source changes and local checks. Live account records, deployment, provider use and Codex settings are separate actions.

- Native tutorial wiring has a dedicated writer. Other agents provide bounded reference or test work. Root owns integration, shared source files and the evidence report.
